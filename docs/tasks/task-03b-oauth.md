## What to do
Put the code in `src/api/oauth/` (routes, consent page) and `src/shared/oauth.ts` (grant, code and token logic that the CLI shares). Every refusal is a plain OAuth error (RFC 6749 §5.2 JSON on `/oauth/token`, RFC 7591 errors on `/oauth/register`); no response says more than the spec needs.

### 1. Discovery and the 401 challenge (§9.3)
- `GET /.well-known/oauth-protected-resource/mcp` and the same document at `/.well-known/oauth-protected-resource`: `resource` (`PUBLIC_API_URL/mcp`), `authorization_servers` (`[PUBLIC_API_URL]`), `bearer_methods_supported: ["header"]`; no `scopes_supported`. `GET /.well-known/oauth-authorization-server` with exactly the §9.3 fields, including `authorization_response_iss_parameter_supported`. No OpenID document (404). Public, no auth, `Access-Control-Allow-Origin: *` on these GETs only.
- Extend `bearerChallenge` so `/mcp` returns `Bearer realm="nacre", resource_metadata="<PUBLIC_API_URL>/.well-known/oauth-protected-resource/mcp"` (no `scope`; the spec example omits `realm`, keep it and say so). `/v1/*` keeps the plain challenge. Update the task 3 tests that assert the old string.

### 2. Dynamic client registration (`POST /oauth/register`, RFC 7591)
- JSON body (capped at a few KB). Public clients only: `token_endpoint_auth_method` absent or `none`, anything else is `invalid_client_metadata`. `redirect_uris` required, 1–5 entries, each `https` or loopback (`http://127.0.0.1`, `http://[::1]`, `http://localhost`), no fragment, no userinfo, else `invalid_redirect_uri`. `client_name` capped in length. Ignore unknown fields but keep the request as received in `metadata`.
- Insert `oauth_clients` (`cli_<ulid>`), respond `201` with `client_id`, `client_id_issued_at`, the accepted metadata and **no secret**. Log `oauth_client_register`. **Rate limit 10 an hour**, process-wide, in memory (one `api` instance; say in the PR that a restart resets it), `429` with `Retry-After`.
- An unapproved client (`approved_at` null) older than 24 hours is treated as unknown everywhere (no delete; `nacre_app` can't). A client with `disabled_at` set is refused.

### 3. `/oauth/authorize` and the consent page
- `GET` validates in this order: client known, enabled and not expired, and `redirect_uri` **exactly** equal to a registered one. Any failure there renders an error page and **never redirects**. After that, errors redirect to the redirect URI with `error`, `state` and `iss`: `response_type=code` only; `code_challenge` required with `code_challenge_method=S256` (`plain` or missing is `invalid_request`); `resource`, if present, must equal `mcpResource(config)` (`invalid_target`), and defaults to it. `state` is optional and echoed.
- Valid: render the consent page. Server-rendered and tiny (Hono JSX, which needs `jsx`/`jsxImportSource` in both tsconfigs; or an escaping template helper, your call), **no script and no cookie, set or read**. It works **identically for every OAuth client: no agent id is hardcoded, defaulted or special-cased anywhere** (Marcus's decision, Oct 24). It shows the registering client's **`client_name`** (from dynamic registration; untrusted text, HTML-escaped, shown as `(unnamed client)` if absent) and the **redirect URI's host** (with a warning when loopback), then the agent choice (see "Agent choice" below), a password field, and Approve and Deny. Headers: `Content-Security-Policy: default-src 'none'; style-src 'unsafe-inline'; frame-ancestors 'none'; base-uri 'none'` (no `form-action`, Chrome applies it to the post-submit redirect), `X-Frame-Options: DENY`, `Cache-Control: no-store`, and **`Referrer-Policy: same-origin`, not `no-referrer`** (browsers send `Origin: null` on form posts under `no-referrer`, which the Origin check would reject).
- **Agent choice** (no script, so the controls are plain form fields): an agent `<select>` listing every enabled agent plus a **"Create new agent"** option, and a text input for the new agent's id, always visible, prefilled with a **slug derived from `client_name`** and editable. **Preselection (Marcus's decision, Oct 24):** if an existing **enabled** agent's id equals the slug derived from `client_name` (the unsuffixed slug, before any `-2`), the select preselects that agent; otherwise it preselects "Create new agent". The owner can change the choice either way. This is how a second consent for the same client name, or a client that was revoked and reconnected (a new `cli_` id, the same name), lands on its existing agent instead of creating `-2`. Matching is exact on the id and a suggestion only: nothing is chosen without the owner's Approve, and there is no special-casing of any particular name. Put the derivation in `src/shared/oauth.ts` as `suggestAgentId(clientName, agents)`, where `agents` is every agent row (id and enabled flag), and have it return `{ slug, matchedAgentId, newAgentId }`: `slug` is the base slug, `matchedAgentId` is the enabled agent whose id equals `slug` (or `null`), and `newAgentId` is what the create-new input is prefilled with. Slug rules: Unicode-normalize (NFKD) and drop diacritics, lowercase, turn every run of non-`[a-z0-9]` into one `-`, trim `-`, cut at 32 characters; `Grok Bot` gives `grok-bot`. If the result is empty it becomes `agent`; if it doesn't start with a letter, prefix `agent-`. `newAgentId` is `slug` if no agent row has that id; if one does (it is disabled, or it is enabled but the create-new path is reached anyway), append `-2`, `-3`, … until free, so create-new never collides (a **disabled** agent is never preselected and its id counts as taken). When `matchedAgentId` is set the create-new input is still prefilled with `newAgentId` (that is `slug-2`, since `slug` exists), so switching to "Create new agent" works without typing. Validation (shared helper `isValidAgentId`, also usable by the CLI later; don't change task 3's `nacre token create` behavior in this PR): `^[a-z][a-z0-9]*(-[a-z0-9]+)*$`, 2–32 characters, not `owner`, `worker` or `system` (spec §4; those are activity-log actors). The input says it is used only when "Create new agent" is selected.
- **On approval, server-side:** a `select` value other than the create-new marker must be the id of an **existing enabled agent**, else re-render with an error (never trust the form). For create-new, validate the id (re-render with `422` and the field's error, keeping the owner's input except the password) and reject an id that already exists (the owner can pick it from the list instead; the page preselects that agent when it matches the client's name). The new `agents` row (`agent_id` = the slug, `display_name` = `client_name` trimmed to 80 characters or the id, `client_kind` `mcp-oauth`) is inserted **in the same transaction as the auth code and `approved_at`**, only after the signature and password checks pass; a failed approval creates nothing. Deny never creates an agent.
- The validated request (client, redirect URI, challenge, resource, state) travels in a signed hidden field: HMAC with a key derived from `TOKEN_PEPPER` (e.g. `HMAC(TOKEN_PEPPER, "nacre-consent-v1")`), 10-minute expiry, verified in constant time. Never trust other form fields: the agent choice and password are the only ones read, and both are validated server-side.
- `POST /oauth/authorize`: `originCheck([PUBLIC_API_URL], { required: true })` first (only the api's own origin, not the app origin), then the signature, then the password. **Owner password (confirmed by Marcus, Oct 24):** the `OWNER_PASSWORD_HASH` variable holds an **argon2id** PHC string, produced by `nacre owner-password hash` (spec §12.1). Verify with Node 24's `crypto.argon2Sync` (added in 24.7; read the params from the stored hash, compare with `timingSafeEqual`; if the pinned Node lacks it, use `@node-rs/argon2` and say so). Add `nacre owner-password hash`: reads the password from a no-echo prompt (or stdin when piped), refuses under 12 characters, prints only the PHC string. Never log or echo the password or the hash. Wrong password: re-render with a generic message, `403`, request log only (public, permanent rows are not allowed here, as in task 3). **Rate limit** wrong passwords, process-wide, in memory (5 in 15 minutes, then `429`); say why in the PR. If `OWNER_PASSWORD_HASH` is unset the consent POST returns `503` and the api still starts, so merging before the variable is set can't break Claude Code's `/mcp`.
- Approve: set `approved_at` if null (first approval), create the chosen new agent (above), insert an auth code (32 random bytes, `HMAC(TOKEN_PEPPER, code)` as `code_hash`, `grant_id` `grt_<ulid>`, bound to client, redirect URI, challenge, resource and agent; `expires_at` 5 minutes), and `303` to the redirect URI with `code`, `state` and `iss`. Deny: `303` with `error=access_denied`. Log `oauth_consent` for both (actor `owner`, `details.decision`, client, agent, grant, redirect host; never the code). When approval creates an agent, the same entry carries `details.agent_created: true` with the new `agent_id`: spec §13.2 has no separate agent-creation kind and `activity_log.kind` is typed in `logActivity`, so **don't add one**; mention in the PR that an `agent_create` kind would be a spec change if Marcus wants it.

### 4. `/oauth/token` (form-encoded; `Cache-Control: no-store`, `Pragma: no-cache`)
- **`authorization_code`**: consume the code atomically (`UPDATE … SET used_at = now() WHERE code_hash = … AND used_at IS NULL AND expires_at > now() RETURNING`). Check `client_id`, exact `redirect_uri`, PKCE (`base64url(SHA-256(code_verifier))` equals the stored challenge; verifier 43–128 chars), and `resource` if sent. An already-used code revokes the whole grant and logs `oauth_refresh_reuse` (`details.what = "code"`); an expired or unknown code is just `invalid_grant`. Issue an access token (1 hour) and a refresh token (30 days from issue) as `agent_tokens` rows: `kind` `oauth_access` / `oauth_refresh`, `oauth_client_id`, `grant_id`, `resource`, the code's agent, an expiry, full scope (the defaults), minted with `mintToken` so the format and HMAC are task 3's. Response: `access_token`, `token_type: "Bearer"`, `expires_in: 3600`, `refresh_token`; no `scope`.
- **`refresh_token`**: parse and HMAC-check the token, check kind, client, not revoked, not expired, agent and client enabled. Rotate atomically (`UPDATE … SET rotated_at = now() WHERE token_id = … AND rotated_at IS NULL RETURNING`): issue a new pair in the same grant. If the token was already rotated (or the update matches nothing because of a race), **revoke every token in the grant** and log `oauth_refresh_reuse` (`details.what = "refresh"`, token and grant ids). Don't let two concurrent refreshes both win.
- Log `token_create` once per success (the access token as `token_id`, `details` with kind, grant, refresh token id and `via`). Any other grant type is `unsupported_grant_type`. No client secrets are accepted; `client_id` is required.
- `nacre token revoke <token_id>` now revokes **the whole grant** when the token has a `grant_id` (one `token_revoke` entry listing the count), keeps task 3's behavior for static tokens, and `nacre token list` also shows `grant_id`.
