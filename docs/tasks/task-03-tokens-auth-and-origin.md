## What to do

### 1. Config and the runtime database
- api config (zod, `src/shared/config.ts`): require **`DATABASE_URL`** (connects as `nacre_app`), **`TOKEN_PEPPER`** (at least 32 characters) and **`PUBLIC_API_URL`**; optional `PUBLIC_APP_URL` and `ALLOWED_ORIGINS` (comma-separated, default `PUBLIC_API_URL` plus `PUBLIC_APP_URL`). **Remove `NACRE_DEV_TOKEN`** from code, `.env.example`, tests and `.railway/railway.ts`. The worker doesn't need the database until task 5.
- Wire `createSql(DATABASE_URL)` into api startup and close it on shutdown. `/healthz` runs `SELECT 1` and returns 503 with `db: "error"` if it fails, so a wrong `nacre_app` password shows up on deploy.
- A small ID helper (`src/shared/ids.ts`, e.g. the `ulid` package): `newId('tok')` gives `tok_<26-char ULID>`, and `act_` works the same way. Agent IDs stay plain names such as `claude-code`.

### 2. Tokens and the CLI (§4, §7, §8.1)
- Format **`nacre_tok_<ulid>_<secret>`**: the `token_id` (`tok_<ulid>`) is the public prefix stored as the row key; the secret is 32 random bytes, base64url. Store `secret_hash = HMAC-SHA256(TOKEN_PEPPER, secret)`; never store or log the secret. Parse by fixed positions, because base64url secrets can contain `_`.
- A `nacre` CLI in `src/cli/`, compiled into `dist/` so it runs inside the deployed image (`node dist/cli/main.js …`; `pnpm nacre …` locally). It uses `DATABASE_URL` and `TOKEN_PEPPER`, like the api.
  - `nacre token create --agent <agent_id> [--client-kind <kind>] [--note <text>] [--expires-at <iso>]`: creates the `agents` row if missing (display name = id, `client_kind` default `cli`), inserts a `static` token with the §4 defaults, prints **only the token on stdout** and `token_id`, agent and "shown once" on stderr, and writes a `token_create` entry.
  - `nacre token revoke <token_id>`: sets `revoked_at` (any kind; grant-wide revoke is 3b), writes `token_revoke`, and is a no-op with a clear message if already revoked.
  - `nacre token list`: `token_id`, agent, kind, created, last used, expires, revoked. Never secrets or hashes.

### 3. One verifier and middleware (§7, §9.3)
- `verifyToken(header, route: 'mcp' | 'v1')` in `src/api/auth.ts`, used by a Hono middleware on `/mcp` now and on `/v1/*` from task 4. **Don't use the SDK's `requireBearerAuth`**: it rejects tokens with no expiry, and static tokens have none (§9.3 note). Rules: well-formed `Authorization: Bearer` header; row exists; `timingSafeEqual` on the HMAC; not revoked; not expired (if `expires_at` is set); agent not disabled; `oauth_refresh` is never a bearer token; `oauth_access` only on `route = 'mcp'` and only if `resource = PUBLIC_API_URL + '/mcp'` (A17.5's logic, tested here); `static` works on both routes.
- Every failure gets the same 401 with `WWW-Authenticate: Bearer realm="nacre"`, built by one challenge function that 3b changes to add `resource_metadata`. The body never says why.
- **Tokens in the URL are rejected**: any `access_token` or `token` query parameter, or any query value that looks like `nacre_tok_…`, gets a 401 even with a valid header. The request log keeps logging the path only.
- On success: update `last_used_at`, put `{ agentId, tokenId, kind, scopes… }` on the Hono context, and pass it to the MCP handler as the SDK's `authInfo` (`handler.fetch(request, { authInfo })`), so tools can see who is calling.

### 4. Activity log helper (§13.2)
- `logActivity(sqlOrTx, entry)` in `src/shared/activity.ts`: generates `act_<ulid>`, inserts one `activity_log` row, accepts a transaction so task 4 can log in the same transaction as the event. Type `kind` as the §13.2 union. It throws if any field contains something shaped like a token.
- **`token_use_denied`**: written when a *well-formed* token is rejected (actor = the row's `agent_id`, `token_id` set only if the row exists, `details.reason` = `revoked`, `expired`, `bad_secret`, `wrong_resource`, …). No entry for a missing or malformed header (OAuth discovery probes would flood the log). A logging failure never turns a 401 into a 500.
- **Migration `system` entry** (deferred from task 2): the deploy migration step writes one `system` entry (actor `system`, `details.applied` = the versions) when it applied something, and none when nothing was pending. It must work in the runtime image (no `tsx`), so wrap dbmate in a compiled command (e.g. `nacre db migrate`) and make `db:predeploy` use it. **The pre-deploy step must still run the verifier after migrating** (PR #21), so a broken guard keeps stopping the deploy. Keep `pnpm db:migrate`, `pnpm db:verify` and `pnpm db:predeploy` working locally, and keep CI running `pnpm db:predeploy` after `pnpm build`.
- **`nacre_app` login from a Railway variable** (replaces task 2's manual psql step, which PR #21 removed): the same pre-deploy step, as the owner, reads an optional `NACRE_APP_DB_PASSWORD` and, when set, runs `ALTER ROLE nacre_app LOGIN PASSWORD …` (idempotent, every deploy, so rotating the variable rotates the password). The password is passed as a parameter or safely quoted, never logged, and never written to a migration. When it is unset, leave the role alone and print one line saying so. Order: migrate, set the login, then verify (the verifier must still pass with `LOGIN` on).

### 5. Origin check on `/mcp` (§11, A11)
- Middleware on `/mcp`, before auth: no `Origin` header passes; a present `Origin` not in the allow-list (exact scheme, host and port), or an unparsable one such as `null`, gets **403**. Write it as a small helper that 3b reuses for the consent form. (The SDK's `originValidationResponse` matches hostnames only, ignoring scheme and port. Use it only if you say why in the PR.)

Don't declare settings that equal Railway's defaults (PR #23 dropped `api`'s `restartPolicyType: ON_FAILURE` for this reason). Update the header comment.
